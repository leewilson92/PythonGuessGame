## 1. 背景与问题

当前 App 的几类核心对象只做了一部分增删查改（CRUD），缺口会直接挡住日常使用：

- **交易（Transaction）**：
  - 增 = `AddTransactionView`「记一笔」已做。
  - 删 = `TransactionListView` 交易行左滑 `swipeActions` 删除已做。
  - 查 = 列表按日期分组已做。
  - **改 / 详情 = 缺**：列表里的交易行**点不动**（`TransactionRow` 没有任何点击进入），既看不到单笔完整信息，也无法修改。一旦记错（金额按错、选错分类/支付方式、日期不对、漏了优惠），用户只能删掉重记——违背"记一笔要快、不添堵"的定位。
- **分类（Category）**：由 `Sources/Seed/SeedData.swift` 首启种入 11 项（餐饮/交通/购物/日用/居住/通讯/娱乐/医疗/人情 + 收入工资/其他），但**没有任何管理界面**，用户无法新增自己的分类、改名/改图标、删除用不上的。模型 `Category` 已留 `name / icon / kind / sortIndex` 字段与注释「用户可增删改」，但 UI 缺位。
- **支付方式（PaymentMethod）**：同样首启种入 4 项（微信/支付宝/银行卡/信用卡），**没有管理界面**。而"多卡对比"是本 App 的差异化卖点之一，用户大概率要加自己的几张银行卡/信用卡才能让对比有意义。PRODUCT_PLAN 明确写过「支付方式用户自定义增删」，属计划内但未实现。

与产品定位的关系：补全 CRUD 是把"能用"补成"好用"。交易编辑要复用「记一笔」的表单体验，不引入新交互负担；分类/支付方式管理是低频配置，放在不打扰日常记账的位置即可。全程仍然本地、无网络、无注册、无广告。

## 2. 目标与用户价值

- **交易可改 + 可看详情**：记错能直接改，而不是删了重记；点开一笔能看到这笔的全部信息。
- **分类可管理**：用户按自己的生活习惯增删改分类，让记账归类更贴合自己。
- **支付方式可管理**：用户加上自己真正在用的卡，"多卡对比"才有意义。
- 版本归属：属 **MVP 收尾**（把已规划但未落地的基础能力补齐），不是新阶段功能。不触及 v2 的资产/收入/同步等范畴。

## 3. 用户故事

- 作为记账的人，我刚记的一笔金额按错了，我想**点开这笔直接改金额并保存**，以便不用删掉重记。
- 作为记账的人，我想**点一下某笔交易看它的完整详情**（含原价/优惠、支付方式、日期、备注、收支类型），以便核对自己记得对不对。
- 作为记账的人，我发现某笔选错了分类或支付方式，我想**在编辑里改过来**，以便统计和多卡对比准确。
- 作为有特定消费习惯的人，我想**新增一个自己的分类**（如"宠物""健身"），以便归类更贴合我的生活。
- 作为想让分类清爽的人，我想**删掉/改名我用不上的内置分类**，以便记账时分类列表不冗长。
- 作为有多张卡的人，我想**新增我自己的银行卡/信用卡作为支付方式**，以便逐笔记到对应卡上、让"哪张卡最省"的对比有意义。
- 作为已经记了不少账的人，当我删除一个仍被历史交易引用的分类/支付方式时，我想**清楚地知道这些历史交易会变成什么**（而不是悄悄丢数据或让金额对不上）。

## 4. 功能需求

> 优先级：P0 = 本期必做；P1 = 本期尽量做；P2 = 可推迟（视开放问题结论决定是否纳入本期）。
> 标 ⚠️ 的条目其最终行为**取决于第 8 节开放问题的结论**，确认前不进入技术设计。

### A. 交易（Transaction）

- **FR-A1（P0）交易详情页**：在记账列表点一下某条交易行，进入**只读详情页**，展示这笔交易的完整信息。具体展示哪些字段见开放问题 Q3，至少包含：收支类型、实付金额、分类、支付方式、日期、备注；有原价时展示原价与"省下"金额。
- **FR-A2（P0）详情页进入编辑**：详情页右上角有「编辑」入口，点击进入**编辑表单**。
- **FR-A3（P0）全字段编辑**：编辑表单可修改交易的**全部字段**——收支类型（支出/收入）、实付金额、原价/优惠（可加可去）、分类、支付方式、日期、备注，字段集合与交互**与「记一笔」表单保持一致**（同样的金额键盘优先、分类选择、优惠开关、支付方式选择、日期、备注）。
- **FR-A4（P0）保存即生效**：编辑保存后，记账列表、按日分组的当日支出小计、以及概览页的派生数字（本月支出 / 现金流出 / 优惠合计 / 最省的卡）都应随之更新；取消则不改动原交易。
- **FR-A5（P0）保存校验**：与「记一笔」一致——实付金额必须 > 0 才能保存（`canSave` 同款规则）。
- **FR-A6（P1）删除入口一致性**：保留列表左滑删除；详情页内**可考虑**也提供删除入口（见开放问题 Q4）。

### B. 分类（Category）

- **FR-B1（P0）分类列表管理页**：提供一个分类管理界面，列出现有分类（建议按收支类型分组或区分，因为分类带 `kind`），可进入新增/编辑。入口位置见开放问题 Q5。
- **FR-B2（P0）新增分类**：用户可新增分类，至少需填名称、选图标（SF Symbol）、选所属收支类型（支出/收入）。
- **FR-B3（P0）编辑分类**：可改名称、图标 ⚠️（是否允许改内置种子项见 Q2）。是否允许改已有分类的收支类型 `kind` 见开放问题 Q6。
- **FR-B4（P0）删除分类**：可删除分类。⚠️**删除一个仍被交易引用的分类时的行为，见开放问题 Q1（必须先定，关系数据完整性）。**
- **FR-B5（P1）分类排序**：⚠️支持用户调整分类顺序（影响「记一笔」分类宫格的排列）。是否本期做见开放问题 Q2。模型已有 `sortIndex` 字段。
- **FR-B6（P2）自定义图标范围**：⚠️图标可选范围（固定一组预置 / 任意 SF Symbol 搜索）见开放问题 Q2。

### C. 支付方式（PaymentMethod）

- **FR-C1（P0）支付方式管理页**：提供支付方式管理界面，列出现有支付方式，可进入新增/编辑。入口位置见开放问题 Q5。
- **FR-C2（P0）新增支付方式**：用户可新增支付方式，至少需填名称、选类型（微信/支付宝/银行卡/信用卡/现金，`PaymentType`），图标默认随类型、可选自定义。
- **FR-C3（P0）编辑支付方式**：可改名称、类型、图标 ⚠️（是否允许改内置种子项见 Q2）。
- **FR-C4（P0）删除支付方式**：可删除支付方式。⚠️**删除一个仍被交易引用的支付方式时的行为，见开放问题 Q1。**
- **FR-C5（P1）排序**：⚠️支持调整支付方式顺序（影响「记一笔」支付方式选择的排列、以及默认值逻辑）。模型已有 `sortIndex`。是否本期做见 Q2。

### 跨对象一致性

- **FR-X1（P0）不变量不被破坏**：本期是 CRUD 补全，**不改变任何计费/汇总口径**。信用卡消费仍只在刷卡当时记一次支出；房贷本金不算支出；两种口径（本月支出 / 现金流出）维持不变；金额仍一律 `Decimal`；优惠/负债剩余仍为派生计算、不落库。编辑交易只是改这笔的原始字段，派生值跟着重算。
- **FR-X2（P0）空态友好**：分类/支付方式被删到空时，「记一笔」与编辑表单不应崩溃或卡死（分类宫格可空、支付方式可"未指定"）。

## 5. 验收标准（可测，供 verifier 核对）

### 交易
- AC-1：在记账列表**点一下**任意一条交易行 → 进入该笔的**只读详情页**，页面显示这笔的实付金额、分类、支付方式、日期、备注、收支类型；若这笔有原价，则同时显示原价与"省下 X"。
- AC-2：详情页右上角点「编辑」→ 进入编辑表单，表单中各字段**预填**为这笔交易的当前值（金额、分类、支付方式、日期、备注、收支类型、原价/优惠状态都正确回显）。
- AC-3：在编辑表单把**实付金额**改为另一个值并保存 → 返回后，列表该行金额、该笔所在"当日支出"小计、概览页"本月支出/现金流出"随之更新为新值。
- AC-4：在编辑表单把**分类**改成另一个分类并保存 → 列表该行的图标与分类名更新为新分类。
- AC-5：在编辑表单把**支付方式**改成另一张卡并保存 → 列表该行支付方式更新；若涉及优惠，概览页"最省的卡"按新归属重算。
- AC-6：在编辑表单**给一笔原本无原价的交易补上原价**（原价 > 实付）并保存 → 列表该行出现"省 X"，概览"本月优惠合计"增加对应金额；反之去掉原价则"省 X"消失、优惠合计相应减少。
- AC-7：在编辑表单把某笔从**支出改为收入**（或反向）并保存 → 列表该行金额符号（-/+）与颜色更新，概览"本月支出"相应变化（收入不计入支出口径）。
- AC-8：进入编辑表单后点「取消」→ 原交易保持不变（列表、概览均无变化）。
- AC-9：在编辑表单把实付金额清空或改为 0 → 「保存」按钮不可点（与「记一笔」同款校验）。
- AC-10：列表交易行左滑删除仍可用，删除后列表与概览同步更新（回归，确认未被破坏）。

### 分类
- AC-11：进入分类管理页 → 看到当前所有分类（含首启种子项）。
- AC-12：新增一个分类（填名称、选图标、选收支类型）并保存 → 该分类出现在管理列表，且回到「记一笔」选择对应收支类型时，分类宫格里能选到它。
- AC-13：编辑某分类改名 → 管理列表、「记一笔」宫格、以及引用该分类的历史交易显示的分类名都更新为新名。
- AC-14：删除一个**未被任何交易引用**的分类 → 该分类从管理列表与「记一笔」宫格消失。
- AC-15：删除一个**仍被交易引用**的分类 → 允许删除；删除后这些历史交易显示为"未分类"，其金额与优惠不变、概览数字不受影响（Q1 已定为 `.nullify`）。
- AC-16：在管理页拖动调整分类顺序 → 「记一笔」分类宫格的排列随之改变（Q2 已定本期做排序）。

### 支付方式
- AC-17：进入支付方式管理页 → 看到当前所有支付方式（含首启种子项）。
- AC-18：新增一个支付方式（如"招行信用卡"，选类型信用卡）并保存 → 出现在管理列表，且「记一笔」支付方式选择里能选到它。
- AC-19：编辑某支付方式改名 → 管理列表、「记一笔」选择项、引用它的历史交易显示名、概览"最省的卡"展示名都更新为新名。
- AC-20：删除一个**未被引用**的支付方式 → 从管理列表与「记一笔」选择项消失。
- AC-21：删除一个**仍被引用**的支付方式 → 允许删除；引用它的历史交易显示为"未指定"，金额与优惠不变；概览"最省的卡"重算时忽略已删项（Q1 已定为 `.nullify`）。

### 不变量回归（必测）
- AC-22：信用卡消费仍只算一次支出，"还信用卡"不另记（本期未引入任何重复计路径）。
- AC-23：编辑/删除交易后，概览"本月支出（消费+利息）"与"本月现金流出（含房贷全额）"两个数字仍各自正确、互不混淆。
- AC-24：所有金额展示与运算无浮点误差（仍走 `Decimal`）；优惠、负债剩余等派生值未被落库、由计算得出。

## 6. 范围边界

**本期做：**
- 交易：只读详情页 + 全字段编辑（复用「记一笔」字段集与交互）+ 保存后各处同步。
- 分类：增 / 改 / 删 的管理界面（排序、内置项可否改/删、图标范围见开放问题，按结论纳入）。
- 支付方式：增 / 改 / 删 的管理界面（同上）。
- 保证既有删除、列表、概览不被破坏，且产品不变量不变。

**明确不做 / 推迟：**
- 不改任何**计费 / 汇总口径**与房贷算法（本期纯 CRUD，不碰 `Finance/`、不碰两种口径定义）。
- 不做交易的批量编辑 / 批量删除 / 多选。
- 不做交易搜索、筛选、按分类/支付方式查看明细（属概览/统计增强，另开 PRD）。
- 不做交易的"复制/再记一笔"快捷操作（可列入后续 backlog）。
- 不做分类/支付方式的合并（把 A 并入 B 并迁移历史交易）——比单纯增删改复杂，单列后续。
- 不引入新的对象类型；不碰 v2 的资产、收入端、iCloud 同步、Face ID。
- 软删除 / 归档（仅隐藏不真删）是否需要，取决于 Q1 结论；默认本期不引入额外的"归档"状态，除非 Q1 选了软隐藏方案。

## 7. 对现有功能与数据的影响

**受影响的现有页面 / 功能：**
- `Views/Transactions/TransactionListView.swift`：交易行从"不可点"变为"可点进详情"；现有左滑删除保留。
- `Views/Transactions/AddTransactionView.swift`：其字段集与交互将作为交易编辑的体验蓝本（是否复用同一表单由 architect 定，PRD 只要求体验一致）。
- `Views/Settings/SettingsView.swift` 与管理入口：**现状更正**——`SettingsView`（备份）当前经 `OverviewView` 右上角齿轮（`gearshape`，sheet 弹出）**可达，并非死代码**。本期改为新增第 4 个 Tab「我的」承载 设置/分类管理/支付方式管理/备份，并移除概览齿轮避免双入口（见第 0 节）。
- `Views/Overview/OverviewView.swift` 与 `Finance/MonthlySummary.swift`：本身不改，但要保证交易编辑/删除后其派生数字正确刷新（SwiftData 查询应自动反映）。

**数据 / 模型影响：**
- `Transaction`、`Category`、`PaymentMethod` 三个 `@Model` 已具备本期所需字段（含 `sortIndex`、`.nullify` 的反向关系），**预计无需新增字段**即可支持增删改 + 排序；除非 Q1 选择"软隐藏"方案，可能需要给 Category/PaymentMethod 加一个"隐藏/归档"标志位——这属于实现层，由 architect 据 Q1 结论定。
- 删除分类/支付方式涉及 SwiftData 删除规则与历史交易引用，是本 PRD 最需要先拍板的产品决策（见 Q1）。当前模型 `Transaction.category` / `Transaction.paymentMethod` 都是 `deleteRule: .nullify`（删除分类/支付方式时交易上的引用置空，即变"未分类/未指定"），这只是现状默认，**最终策略以 Q1 用户确认为准**。
- 备份导出/导入（`BackupManager`）：本期不主动改其格式；若 Q1 引入新字段（如归档标志），architect 需评估备份兼容性（属实现层关注点，PRD 在此点名提示）。

**产品不变量核对：**
- 信用卡不重复计：本期不新增任何"还卡"记账路径，不受影响。✅
- 房贷本金不算支出：本期不碰房贷与汇总口径。✅
- 两种口径并存：定义不变，仅保证编辑/删除后重算正确。✅
- 金额 `Decimal`：编辑沿用同款金额解析，不引入 `Double`。✅
- 派生值不落库：优惠、负债剩余仍计算得出；编辑只改原始字段。✅

> 6 个开放问题已由用户全部拍板，**最终结论见第 0 节决策表**。下面保留各问题的原始候选方案，作为决策背景/依据；落地一律以第 0 节为准。

- **Q1（最关键，关系数据完整性）删除"正在被交易引用的分类/支付方式"时怎么处理？** 三类候选方案，请用户选其一（分类与支付方式可分别选，也可统一）：
  - (a) **禁止删除**：被引用时不允许删，提示"该分类下还有 N 笔交易，无法删除"（最安全，但用户想删得先处理掉历史交易）；
  - (b) **置为未分类 / 未指定**：允许删，历史交易的该字段置空（对应现状 `.nullify`，这些交易在列表/统计里显示"未分类""未指定"，金额与优惠不丢）；
  - (c) **软隐藏 / 归档**：不真正删除，仅从「记一笔」可选项里隐藏，历史交易仍挂在它名下（需要给模型加"隐藏"标志，备份与统计要处理隐藏项）。
  > 这一项直接决定模型是否加字段、删除规则、以及 AC-15 / AC-21 的具体验收，**必须最先定**。
- **Q2 内置种子项可否编辑/删除？是否本期支持排序与自定义图标？**
  - 内置的分类（餐饮/交通…）和支付方式（微信/支付宝…）是否**允许用户改名、改图标、删除**？还是内置项锁定、只能增删自己加的？
  - **排序**（FR-B5 / FR-C5）是否本期就做？模型已有 `sortIndex`，做了能让常用分类排前面，但增加交互复杂度。
  - 图标（FR-B2 / FR-B6）选择范围：给一组**固定预置图标**让用户挑（简单、可控），还是支持**任意 SF Symbol 搜索/输入**（灵活但更复杂、易选到不存在的符号）？倾向极简的话建议固定预置组。
- **Q3 交易详情页具体展示哪些字段、以什么形式？** 至少含：收支类型、实付金额、分类、支付方式、日期、备注、（有则）原价与"省下"。是否还要展示：创建/记录时间？是否需要在详情页直接显示"这笔属于本月支出口径还是仅现金流"之类的口径说明（一般交易都计入，可能没必要）？详情页是简单的字段罗列，还是要突出金额大字 + 次要信息？
- **Q4 详情页是否提供"删除"按钮？** 现在删除只在列表左滑。详情页内是否也放一个删除入口（更显眼、好找）？若放，删除后应直接返回列表。
- **Q5 分类 / 支付方式管理页放在哪个入口？**（更正：`SettingsView` 原经概览页齿轮可达，并非不可达）候选：
  - (a) 在记账列表页右上角加一个"设置/管理"入口（齿轮），打开设置页，内含"分类管理""支付方式管理""数据备份"几项；
  - (b) 新增第 4 个 Tab（如"我的/设置"）；
  - (c) 其他位置。
  > 这关系到信息架构，且顺带解决"设置页目前进不去"的问题，请用户定方向。
- **Q6 编辑交易时改"收支类型"、以及编辑分类时改分类的"收支类型 `kind`"，允许吗？**
  - 交易侧：编辑时把一笔从支出改成收入（FR-A3 / AC-7）已默认允许（与「记一笔」一致）；请确认这符合预期。
  - 分类侧：一个已存在、且可能已被交易引用的分类，是否允许把它的 `kind` 从支出改成收入（反之亦然）？这会让引用它的历史交易出现"收支类型与分类类型不一致"的情况，可能需要禁止或限制。请用户定。
